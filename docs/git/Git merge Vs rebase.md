`Merge` и `Rebase` — две самые важные операции в Git для интеграции изменений.
Давайте разберем подробно.

## **Основная концепция**

Представьте, что у вас есть история коммитов:

```
A---B---C  ← main
     \
      D---E  ← feature
```

**Цель обеих команд:** перенести изменения из ветки `feature` в `main`.

## **1. MERGE (слияние)**

### **Что делает:**
Создает **новый коммит слияния**, который объединяет изменения двух веток.

```bash
# Находясь в ветке main
git checkout main
git merge feature
```

**Результат:**
```
A---B---C---F  ← main
     \       /
      D---E    ← feature
```

### **Как работает:**
1. Находит общего предка (B)
2. Создает коммит (F), который содержит изменения из C + D + E
3. Сохраняет историю обеих веток

### **Типы merge:**

#### **Fast-forward merge** (если main не менялся):
```
До: A---B---C  ← main
           \
            D---E  ← feature

После: A---B---C---D---E  ← main, feature
```

```bash
# Git сделает fast-forward автоматически если возможно
git merge feature

# Запретить fast-forward (всегда создавать merge-коммит)
git merge --no-ff feature
```

#### **3-way merge** (если main изменился):
```
До: A---B---C---F  ← main
         \
          D---E    ← feature

После: A---B---C---F---G  ← main
               \       /
                D---E    ← feature
```

### **Плюсы merge:**
- **Проще** для начинающих
- **Сохранение истории** — видно, где была ветка
- **Меньше конфликтов** в целом

### **Минусы merge:**
- **Загромождает историю** merge-коммитами
- **Сложнее читать** линейную историю

## **2. REBASE (перебазирование)**

### **Что делает:**
"Перемещает" вашу ветку на конец другой ветки, **переписывая историю**.

```bash
# Находясь в ветке feature
git checkout feature
git rebase main
```

**Результат:**
```
До: A---B---C  ← main
         \
          D---E  ← feature

После: A---B---C---D'---E'  ← main, feature
```

### **Как работает:**
1. Находит общего предка (B)
2. Временно сохраняет изменения D и E
3. Применяет D и E поверх C (как будто вы их сделали после C)
4. Создает новые коммиты D' и E'

### **Пошаговый процесс rebase:**
```bash
# 1. Перейти на ветку feature
git checkout feature

# 2. Начать rebase на main
git rebase main

# Если есть конфликты:
# Git остановится на каждом конфликтном коммите
# Решить конфликты, затем:
git add .
git rebase --continue

# Или отменить rebase:
git rebase --abort
```

### **Интерактивный rebase (очень мощный!):**
```bash
git rebase -i main
```

Откроется редактор со списком коммитов:
```
pick a1b2c3d Добавил фичу X
pick b2c3d4e Исправил баг
pick c3d4e5f Добавил тесты
```

Можно:
- **reword** — изменить сообщение коммита
- **edit** — остановиться для редактирования коммита
- **squash** — объединить с предыдущим коммитом
- **fixup** — объединить, но отбросить сообщение
- **drop** — удалить коммит

### **Плюсы rebase:**
- **Чистая линейная история** — нет merge-коммитов
- **Легче читать** историю изменений
- **Можно редактировать историю** (интерактивный rebase)

### **Минусы rebase:**
- **Переписывает историю** — опасно для опубликованных веток
- **Больше конфликтов** — может быть много повторных решений
- **Сложнее для понимания** новичкам

## **3. КОГДА ЧТО ИСПОЛЬЗОВАТЬ?**

### **Использовать MERGE когда:**
1. **Ветка публичная** (другие разработчики с ней работают)
2. **Хотите сохранить историю** ветвления
3. **Простой проект** с небольшой командой
4. **Не важно** наличие merge-коммитов

### **Использовать REBASE когда:**
1. **Локальная ветка** (еще не отправили на сервер)
2. **Хотите чистую линейную историю**
3. **Нужно подготовить PR** (pull request) к мержу
4. **Исправляете старые коммиты** в своей ветке

## **4. ПРАКТИЧЕСКИЕ СЦЕНАРИИ**

### **Сценарий 1: Подготовка фичи к мержу**
```bash
# На feature-ветке
git rebase main  # сделать актуальной
# Решить конфликты если есть
git checkout main
git merge feature  # fast-forward сработает
```

### **Сценарий 2: Обновить feature-ветку с изменениями из main**
```bash
# Способ 1: merge
git checkout feature
git merge main
# История: feature ← main влит в feature

# Способ 2: rebase (предпочтительнее)
git checkout feature
git rebase main
# История: feature переставлена на конец main
```

### **Сценарий 3: Объединить несколько коммитов в один**
```bash
# На feature-ветке
git rebase -i HEAD~3
# В редакторе: первые коммиты оставить pick, остальные сделать squash
```

## **5. GOLDEN RULES (золотые правила)**

### **Правило 1: Не rebase опубликованную историю**
```bash
# НИКОГДА НЕ ДЕЛАЙТЕ ЭТОГО:
git push --force  # после локального rebase

# Лучше (безопасный force push):
git push --force-with-lease
```

### **Правило 2: Rebase для локального упорядочивания**
```
Ваша локальная ветка: делайте rebase сколько хотите
Ветка на GitHub: только merge (или аккуратный rebase)
```

### **Правило 3: Решайте конфликты один раз с rebase**
```
С rebase: решаете конфликты при rebase
С merge: решаете конфликты при merge (один раз)
```

## **6. НАГЛЯДНОЕ СРАВНЕНИЕ**

### **История после merge:**
```
*---*---*---M  ← main
     \     /
      *---*    ← feature
```

**Плюсы:**
- Видно ветвление
- Легко отменить (revert merge-коммит)

### **История после rebase:**
```
*---*---*---*---*  ← main (и feature)
```

**Плюсы:**
- Линейно и чисто
- Легко следовать за изменениями

## **7. КОМАНДЫ ДЛЯ РАБОТЫ С КОНФЛИКТАМИ**

### **При merge:**
```bash
git merge feature
# Конфликт? Решаем в файлах, затем:
git add .
git commit  # Создаст merge-коммит
```

### **При rebase:**
```bash
git rebase main
# Конфликт? Решаем в файлах, затем:
git add .
git rebase --continue  # Перейдет к следующему коммиту
```

## **8. РЕКОМЕНДАЦИЯ ДЛЯ НАЧИНАЮЩИХ**

1. **Начните с merge** — он безопаснее
2. **Изучите rebase на тестовых репозиториях**
3. **Используйте rebase для:**
    - Очистки истории перед PR
    - Обновления локальной ветки
    - Объединения коммитов

## **9. ВИЗУАЛИЗАЦИЯ**

```bash
# Увидеть историю в виде графа
git log --oneline --graph --all

# Посмотреть что будет при merge
git merge --no-commit feature
git merge --abort  # если не понравилось

# Посмотреть что будет при rebase
git rebase --interactive --exec "echo test" main
```

## **Главный вывод:**
- **Merge** = "Соединить и сохранить историю"
- **Rebase** = "Переписать историю как будто работал на свежей основе"

**Совет:** В командах часто используют гибридный подход — разработчики делают rebase своих веток, а в main делают merge (возможно с --no-ff).

Еще немного про работу с 'rebase':
- делаю feature ветку от основной ветки master;
- пишу код в Intellij IDEA;
- в master ветку вливаются изменения другими разработчиками;
- хочу подтянуть изменения из master с помощью rebase в мою локальную feature ветку - какие мои действия?

---

Отличный сценарий! Это именно тот случай, где **rebase** идеально подходит. Вот пошаговая инструкция для IntelliJ IDEA и командной строки.

## **1. ПОДГОТОВКА ПЕРЕД REBASE**

### **Проверить текущее состояние:**
```bash
# Убедиться, что находитесь в feature-ветке
git checkout feature-branch
git status  # Должны быть на feature-branch

# Посмотреть разницу между ветками
git log --oneline --graph --all
```

### **Сохранить текущую работу (если есть незакоммиченные изменения):**
```bash
# Вариант 1: Закоммитить всё
git add .
git commit -m "WIP: текущие изменения"

# Вариант 2: Stash (временное сохранение)
git stash  # Сохранить изменения без коммита
git stash list  # Проверить сохранённые stash
```

## **2. ОБНОВИТЬ ЛОКАЛЬНУЮ MASTER ВЕТКУ**

```bash
# Переключиться на master и получить изменения
git checkout master
git pull origin master

# ИЛИ одной командой:
git fetch origin master  # Только получить изменения без слияния
```

## **3. ВЫПОЛНИТЬ REBASE**

### **Вариант A: Через командную строку (рекомендуется):**
```bash
# Вернуться в feature-ветку
git checkout feature-branch

# Выполнить rebase на обновлённый master
git rebase master
```

### **Вариант B: Через IntelliJ IDEA GUI:**
1. **Git → Branches** (или правой кнопкой на ветке в нижнем правом углу)
2. Выберите вашу **feature-ветку**
3. **Rebase onto → master**
4. Или: **Git → Rebase...**

## **4. РЕШЕНИЕ КОНФЛИКТОВ (если возникнут)**

### **В IntelliJ IDEA:**
1. IDEA покажет **конфликтующие файлы** красным цветом
2. Откройте файл — увидите **3 панели**:
   - **Left**: Ваши изменения (Current Change)
   - **Middle**: Результат (Merge Result)
   - **Right**: Изменения из master (Incoming Change)
3. Используйте кнопки:
   - **Accept Yours** — взять свою версию
   - **Accept Theirs** — взять версию из master
   - **Merge** — ручное редактирование
4. После решения всех конфликтов:
   - **Git → Resolve Conflicts** (отметить как решённые)
   - Или в командной строке: `git add .`

### **В командной строке:**
```bash
# Если rebase остановился из-за конфликта:
# 1. Редактируем файлы вручную или через IDE
# 2. Добавляем исправленные файлы:
git add <файл-с-конфликтом>

# 3. Продолжаем rebase:
git rebase --continue

# 4. Если хотите пропустить этот коммит:
git rebase --skip

# 5. Если всё пошло не так — отменить:
git rebase --abort
```

## **5. ПОСЛЕ УСПЕШНОГО REBASE**

### **Проверить результат:**
```bash
# Убедиться, что история линейная
git log --oneline --graph

# Проверить, что ветка актуальна
git log master..feature-branch  # Покажет ваши уникальные коммиты
```

### **Восстановить stash (если использовали):**
```bash
git stash pop  # Вернуть изменения и удалить stash
# ИЛИ
git stash apply  # Вернуть, но оставить в stash
```

## **6. ВАЖНЫЕ НЮАНСЫ ДЛЯ IDEA**

### **Настройки для удобства:**
1. **Settings → Version Control → Git**:
   - ✅ "Update method: Merge" (для master)
   - ✅ "Rebase instead of merge" (для feature веток)

2. **Для автоматического stash** при rebase:
   - В окне rebase IDEA спросит: "Stash changes before operation?"
   - ✅ **Always Stash** (рекомендуется)

### **Визуализация в IDEA:**
1. **Git → Show Git Log** (Alt+9)
2. Видно как ваша ветка "переехала" на конец master
3. Фиолетовая линия = оригинальная позиция ветки
4. Зелёная линия = новая позиция после rebase

## **7. ЧАСТЫЕ ОШИБКИ И РЕШЕНИЯ**

### **Ошибка: "Your local changes would be overwritten"**
```bash
# Закоммитить или stash:
git stash -u  # Сохраняет даже новые (untracked) файлы
git rebase master
git stash pop
```

### **Ошибка: "Updates were rejected because the tip of your current branch is behind"**
```bash
# Вы запушили ветку ДО rebase, теперь нужно force push
git push origin feature-branch --force-with-lease
# Безопаснее чем --force, проверит что никто не обновил ветку
```

### **Много конфликтов на каждом коммите:**
```bash
# Вместо поэтапного rebase — делаем один merge
git checkout feature-branch
git merge master
# Или используем стратегию "ours"/"theirs"
```

## **8. АЛЬТЕРНАТИВНЫЙ ПОДХОД: MERGE ИЗ MASTER**

Если rebase слишком сложен:
```bash
git checkout feature-branch
git merge master
# Создаст merge-коммит в feature-ветке
# Проще, но история будет менее чистой
```

## **9. ПОЛНЫЙ СЦЕНАРИЙ РАБОТЫ С IDEA**

```bash
# 1. Перед началом работы каждый день
git checkout master
git pull origin master

# 2. Перейти в свою ветку
git checkout feature-branch

# 3. Сделать rebase
git rebase master

# 4. Решить конфликты в IDEA (если есть)

# 5. Продолжить разработку
# ... пишем код ...

# 6. Закоммитить изменения
git add .
git commit -m "Мой новый функционал"

# 7. Если за время работы в master появились новые коммиты:
git checkout master
git pull origin master
git checkout feature-branch
git rebase master  # Быстро, т.к. конфликты уже решены
```

## **10. AUTOSTASH ОПЦИЯ (Git 2.6+)**

```bash
# Автоматически stash и apply
git config --global rebase.autoStash true

# Теперь можно просто:
git rebase master
# Git сам сделает stash → rebase → stash pop
```

## **11. КОГДА НЕЛЬЗЯ ДЕЛАТЬ REBASE:**

1. **Если ветка уже в удалённом репозитории** и с ней работают другие
2. **Если в ветке есть merge-коммиты** (нужно добавить `--rebase-merges`)
3. **Если история очень большая** (сотни коммитов) — будет долго

## **ВИЗУАЛИЗАЦИЯ ПРОЦЕССА:**

```
До rebase:
master:    A---B---C
                      \
feature:               D---E---F

После git pull origin master в master:
master:    A---B---C---G---H
                      \
feature:               D---E---F

После git checkout feature && git rebase master:
master:    A---B---C---G---H
                                  \
feature:                           D'---E'---F'
```

## **СОВЕТЫ ДЛЯ ИНТЕЛЛИДЖЕЙ:**

1. **Используйте горячие клавиши:**
   - `Ctrl+Shift+K` — Commit
   - `Alt+9` — Git Log
   - `Ctrl+T` — Update Project (аналог pull)

2. **Включите авто-импорт Maven/Gradle** чтобы избежать конфликтов в pom.xml

3. **Решайте конфликты через 3-way merge** в IDEA — это удобнее чем в консоли

**Ваш итоговый workflow:**
```
1. Каждое утро: master → pull
2. Перед работой: feature → rebase master
3. Работаем, коммитим
4. Перед push: опять rebase master
5. Push feature
6. Создаём PR/MR
```
