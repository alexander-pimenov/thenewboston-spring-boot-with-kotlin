## 🏗️ **Почему внутренние классы (WindowState, BucketState)?**

### Аналогия с банковским счётом:

```kotlin
// ❌ ПЛОХО: Всё в кучу
class BankAccount {
    var balance: Double = 0.0
    var lastTransactionTime: Instant = Instant.now()
    var accountNumber: String = ""
    var ownerName: String = ""
    // ... и ещё 20 полей
}

// ✅ ХОРОШО: Разделяем ответственность
class BankAccount {
    val accountInfo: AccountInfo  // Информация о счёте
    val balanceState: BalanceState // Состояние баланса и операций
}

data class AccountInfo(val number: String, val owner: String, val type: AccountType)
data class BalanceState(
    val balance: Double, 
    val lastTransaction: Instant,
    val currency: Currency
)
```

**Зачем это нужно?**
- **Организация** - каждая сущность отвечает за свою часть
- **Читаемость** - легче понять что происходит
- **Изменяемость** - можно менять BalanceState не затрагивая AccountInfo

## 🔄 **Почему AtomicReference?**

### Аналогия с сейфом и ключом:

```kotlin
// ❌ ПЛОХО: "Дикий запад" - любой может изменить баланс
class BankAccount {
    var balance: Double = 0.0  // Опасно в многопоточной среде!
}

// ✅ ХОРОШО: "Банковский сейф" - только атомарные операции
class BankAccount {
    private val balanceState = AtomicReference(BalanceState(0.0, Instant.now()))
    
    fun deposit(amount: Double) {
        balanceState.updateAndGet { current ->
            current.copy(balance = current.balance + amount)
        }
    }
}
```

**AtomicReference = сейф с одним ключом**
- Только один поток может изменять состояние в один момент времени
- Гарантирует, что мы всегда работаем с актуальными данными
- Предотвращает `race conditions`

## 🎓 **КОГДА ИСПОЛЬЗОВАТЬ КАКИЕ ПАТТЕРНЫ?**

### Используй **data class** когда:
- Группируешь связанные данные
- Нужна иммутабельность (неизменяемость)
- Хочешь автоматические `equals()`, `hashCode()`, `toString()`

### Используй **AtomicReference** когда:
- Есть состояние, которое меняется в многопоточной среде
- Нужны атомарные операции "прочитать-изменить-записать"
- Хочешь избежать блокировок (synchronized)

### Используй **inner class** когда:
- Класс используется только внутри родительского класса
- Логически связан с родителем
- Упрощает архитектуру

## 🎯 **ПОЧЕМУ ПЕРВЫЙ СПОСОБ ЛУЧШЕ:**

### ✅ **Преимущества одного LinkedHashMap:**

1. **Простота** - меньше кода, меньше ошибок
2. **Автоматическая синхронизация** - не нужно следить за согласованностью двух структур
3. **Встроенная функциональность** - LinkedHashMap уже реализует LRU "из коробки"
4. **Эффективность** - O(1) операции, минимальные накладные расходы
5. **Надёжность** - невозможно рассинхронизировать данные

### ❌ **Проблемы двойного хранения:**
- **Рассинхронизация** - storage показывает 4 элемента, accessOrderMap - 3
- **Утечки памяти** - элементы удаляются из LRU, но остаются в storage
- **Сложность отладки** - трудно отследить где что потерялось
- **Избыточность** - храним те же данные в двух местах
